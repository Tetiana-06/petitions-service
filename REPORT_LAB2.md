# ЗВІТ ПРО ВИКОНАННЯ ЛАБОРАТОРНОЇ РОБОТИ №2

**Тема:** Користувачі, ролі користувачів та розмежування прав доступу  
**Мета:** Розробка мінімально життєздатного продукту з базовою бізнес-логікою, створення бази даних користувачів, налаштування ролей та покриття логіки доступу автоматизованими тестами.  
**Проєкт:** Сервіс місцевих електронних петицій (`petitions-service`)  
**Стек технологій:** Python 3.12/3.14, FastAPI, SQLAlchemy 2.0 (Async), SQLite / PostgreSQL, PyJWT, Passlib (Bcrypt), Pytest, Ruff.

## 2. АРХІТЕКТУРА ТА ОБҐРУНТУВАННЯ ВИБРАНИХ РІШЕНЬ

Схема архітектури безпеки та контролю доступу наведена у файлі [`docs/lab2_architecture.svg`](docs/lab2_architecture.svg).

### 2.1. Чому FastAPI?
- **Асинхронність із коробки (async/await):** забезпечує високу пропускну здатність при операціях введення/виведення з базою даних, що критично для високонавантажених сервісів електронної демократії під час пікових голосувань.
- **Вбудована система Dependency Injection:** дозволяє декларативно перевіряти JWT-токени (`get_current_user`) та ролі (`require_admin`) без дублювання перевірок у тілі кожного маршруту.
- **Автоматична валідація та Swagger:** генерація інтерактивної документації OpenAPI за схемами Pydantic спрощує тестування API.

### 2.2. Чому безсесійний JWT (JSON Web Tokens) замість Cookies/Sessions?
- **Stateless-архітектура:** сервер не зберігає стан сесій в оперативній пам'яті. Це дозволяє масштабувати кількість інстансів бекенду за балансувальником навантаження (наприклад, Nginx) без потреби в централізованому сховищі сесій.
- **Цифровий підпис (HMAC-SHA256):** токен містить корисне навантаження (`sub: username`, `role: user.role`, час життя `exp`), яке клієнт передає в заголовку `Authorization: Bearer <token>`. Сервер перевіряє цілісність токена за допомогою закритого секретного ключа (`SECRET_KEY`).

### 2.3. Безпека паролів: Bcrypt
- Паролі **ніколи не зберігаються у відкритому вигляді**.
- Використовується алгоритм хешування **Bcrypt** із автоматичною генерацією унікальної «солі» (salt) та фактором складності (work factor). Це унеможливлює злом через райдужні таблиці (rainbow tables) та суттєво уповільнює атаки грубої сили (brute-force).

### 2.4. Вертикальне розмежування (RBAC — Role-Based Access Control)
- У системі визначено перелік ролей `UserRole`:
  - `user` — звичайний громадянин.
  - `admin` — адміністратор сервісу петицій.
- Контроль доступу здійснюється залежністю `require_admin`, яка викликається в адмінських маршрутах (`/admin/dashboard`, `/admin/stats`, `/admin/users`, `/petitions/{id}/status`). Якщо поточний користувач не має ролі `admin`, повертається HTTP статус **403 Forbidden**.

### 2.5. Горизонтальне розмежування та захист від IDOR (Insecure Direct Object Reference)
- Атака IDOR виникає, коли авторизований користувач намагається змінити або видалити чужий об'єкт, підставивши його числовий ідентифікатор у URL.
- У системі реалізовано дворівневий захист:
  1. **Сутності предметної області (петиції):** при виклику `PUT /petitions/{id}` сервер перевіряє `petition.author_id == current_user.id`. Якщо користувач намагається змінити чужу петицію, повертається статус **403 Forbidden**.
  2. **Профілі користувачів:** при виклику `PUT /users/{user_id}` перевіряється умова `current_user.id == user_id or current_user.role == 'admin'`. Спроба відредагувати чужий профіль блокується зі статусом **403 Forbidden**.

## 4. ДЕТАЛЬНИЙ ОПИС ВИКОНАННЯ ЗАВДАНЬ

### 4.1. Основні завдання (5 балів)

#### Завдання 1. Модифікація попередньо розробленого проєкту
Проєкт було розширено від попередньої базової структури до повноцінного асинхронного сервісу з інтеграцією механізмів безпеки, таблиць користувачів та бізнес-логіки життєвого циклу петицій.

#### Завдання 2. Створення бази даних користувачів
У файлі `src/models.py` реалізовано таблицю `users`:
```python
class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(Integer, primary_key=True, index=True)
    username: Mapped[str] = mapped_column(String(50), unique=True, index=True, nullable=False)
    hashed_password: Mapped[str] = mapped_column(String(255), nullable=False)
    role: Mapped[str] = mapped_column(String(20), default=UserRole.USER.value, nullable=False)
    full_name: Mapped[Optional[str]] = mapped_column(String(100), nullable=True)
    email: Mapped[Optional[str]] = mapped_column(String(100), nullable=True)
    created_at: Mapped[datetime] = mapped_column(DateTime, default=get_utc_now)
```
Пароль зберігається виключно у вигляді гешу з сіллю. Додано зв'язки з таблицями петицій та підписів.

#### Завдання 3. Реалізація декількох ролей користувачів
Реалізовано перелік:
```python
class UserRole(str, Enum):
    USER = "user"
    ADMIN = "admin"
```
Роль зберігається в базі даних та записується в тіло JWT-токена під час успішного входу: `{"sub": user.username, "role": user.role}`.

#### Завдання 4. Реєстрація для звичайних користувачів
Ендпоінт `POST /auth/register` (`src/main.py`):
- Приймає `username`, `password`, `full_name`, `email`.
- Перевіряє унікальність логіна (повертає `400 Bad Request`, якщо ім'я вже зайняте).
- За замовчуванням призначає роль `user`.
- Гешує пароль за допомогою Bcrypt перед збереженням.

#### Завдання 5. Вхід для різних типів користувачів
Ендпоінт `POST /auth/login` (`src/main.py`):
- Підтримує як стандартну форму `OAuth2PasswordRequestForm` (вимога специфікації OAuth2), так і прямий виклик.
- Знаходить запис користувача та перевіряє пароль функцією `verify_password`.
- При збігу повертає JWT access_token із часом дії (60 хв).
- При помилці логіна чи пароля повертає `401 Unauthorized` із заголовком `WWW-Authenticate: Bearer`.

#### Завдання 6. Домашні сторінки-заглушки для різних типів користувачів
1. **Звичайний користувач:** ендпоінт `GET /users/me`:
   - Захищений залежністю `get_current_user`.
   - Повертає персональне вітальне повідомлення, роль `user`, статус та профільні дані.
   - У веб-інтерфейсі відображається вкладка «Мій кабінет» з можливістю редагувати профіль та переглядати власні петиції.
2. **Адміністратор:** ендпоінт `GET /admin/dashboard`:
   - Захищений залежністю `require_admin`.
   - Повертає вітання адміністратора та підтвердження повного доступу (`Full System Management`).
   - У веб-інтерфейсі відображає розширену статистику (користувачі, петиції, підписи), таблицю користувачів та чергу модерації.

#### Завдання 7. Оновлений код у репозиторії та архітектурне обґрунтування
Код організовано за модульними принципами, налаштовано контроль якості (Ruff) та підготовлено документацію.

### 4.2. Додаткові завдання (5 балів)

#### Додаткове завдання 1 (2 бали). MVP з базовою бізнес-логікою
У системі реалізовано повний життєвий цикл електронної петиції:
1. **Створення петиції (`POST /petitions/`):** авторизований громадянин створює петицію, вказуючи заголовок, опис та цільову кількість голосів.
2. **Перегляд каталогу (`GET /petitions/`):** публічний список петицій із підтримкою повнотекстового пошуку (`?q=...`) та фільтрації за статусом (`?status=active`). Кожен елемент списку містить ім'я автора та динамічно пораховану кількість голосів.
3. **Детальний перегляд (`GET /petitions/{id}`):** відображає прогрес збору підписів у відсотках.
4. **Підписання петиції (`POST /petitions/{id}/vote`):**
   - Дозволено лише автентифікованим користувачам.
   - Система перевіряє, чи не голосував цей користувач раніше за дану петицію.
   - При спробі повторного голосування повертається помилка `400 Bad Request: Duplicate vote`.
   - Фіксується цифровий підпис (геш) та зв'язок з користувачем.
5. **Модерація адміністратором (`PATCH /petitions/{id}/status`):**
   - Тільки користувач із роллю `admin` може перевести статус петиції в `under_review`, `approved` або `rejected`.
   - Звичайний користувач отримує помилку `403 Forbidden`.

#### Додаткове завдання 2 (3 бали). Юніт- та інтеграційні тести з pytest
У файлі `tests/test_auth_access.py` реалізовано повний набір тестів за 4 обов'язковими сценаріями:

1. **Сценарій 1: Анонімний доступ (тест `test_anonymous_access_denied_401`):**
   - Перевірка доступу без токена до `/users/me` -> повертає **401 Unauthorized**.
   - Перевірка доступу без токена до `/admin/dashboard` -> повертає **401 Unauthorized**.
   - Перевірка створення петиції без токена -> повертає **401 Unauthorized**.
   - Перевірка оновлення профілю без токена -> повертає **401 Unauthorized**.
2. **Сценарій 2: Автентифікація та помилки входу (тест `test_authentication_success_and_failures`):**
   - Успішна реєстрація -> **201 Created**.
   - Спроба дублювання логіна -> **400 Bad Request**.
   - Вхід із невірним паролем -> **401 Unauthorized** (`Incorrect username or password`).
   - Вхід під неіснуючим логіном -> **401 Unauthorized**.
   - Вхід із правильними даними -> **200 OK** + JWT токен.
   - Запит до `/users/me` з валідним токеном -> **200 OK**.
3. **Сценарій 3: Вертикальне розмежування ролей (тест `test_vertical_role_separation_403`):**
   - Звичайний користувач звертається до `/admin/dashboard` -> **403 Forbidden** (`Admin privileges required`).
   - Звичайний користувач звертається до `/admin/stats` -> **403 Forbidden**.
   - Звичайний користувач звертається до `/admin/users` -> **403 Forbidden**.
   - Адміністратор звертається до `/admin/dashboard` -> **200 OK**.
   - Адміністратор звертається до `/admin/stats` -> **200 OK**.
4. **Сценарій 4: Горизонтальне розмежування прав / IDOR (тест `test_horizontal_privilege_separation_idor_403`):**
   - Користувач Б намагається змінити петицію Користувача А (`PUT /petitions/{user_a_pet_id}`) -> **403 Forbidden** (`Forbidden: You cannot modify someone else's petition`).
   - Користувач Б намагається змінити дані профілю Користувача А (`PUT /users/{user_a_id}`) -> **403 Forbidden** (`Forbidden: You cannot modify another user's profile`).
   - Автор (Користувач А) змінює власну петицію -> **200 OK**.
   - Користувач А змінює власний профіль -> **200 OK**.
5. **Бізнес-логіка петицій (тест `test_mvp_business_logic_voting_and_moderation`):**
   - Голосування за петицію -> **201 Created**.
   - Повторне голосування тим самим користувачем -> **400 Bad Request** (`Duplicate vote`).
   - Підрахунок голосів у списку -> перевірено збільшення лічильника.
   - Спроба звичайного користувача змінити статус петиції -> **403 Forbidden**.
   - Успішна зміна статусу адміністратором -> **200 OK**.

## 5. ІНСТРУКЦІЯ З ДЕМОНСТРАЦІЇ ВИКОНАНОГО ФУНКЦІОНАЛУ

### Спосіб 1. Через інтерактивний веб-інтерфейс (Найбільш наочний спосіб)

1. Відкрийте термінал у корені проєкту та запустіть сервер:
   ```bash
   uvicorn src.main:app --reload --host 127.0.0.1 --port 8000
   ```
2. Відкрийте в браузері: `http://localhost:8000/`.
3. **Демонстрація швидкого входу та перемикання ролей:**
   - У верхній синій панелі натисніть кнопку **«👑 Admin (admin)»** — система миттєво увійде як адміністратор. У навігації з'явиться бейдж `ADMIN`.
   - Натисніть **«👤 User A (ivan_patriot)»** — система перемкнеться на звичайного користувача з бейджем `USER`.
4. **Демонстрація домашніх сторінок-заглушок:**
   - Перейдіть на вкладку **«👤 Мій кабінет»** — відобразиться персональний кабінет користувача (`/users/me`), де можна оновити своє ім'я або email та переглянути свої петиції.
   - Перейдіть на вкладку **«🛡️ Адмінка»** — відобразиться адмін-панель зі статистикою та модерацією.
5. **Демонстрація бізнес-логіки петицій:**
   - На вкладці **«📋 Каталог»** перегляньте список петицій, пошукайте за словами, натисніть кнопку **«✍️ Підписати»**.
   - Спробуйте натиснути **«✍️ Підписати»** вдруге — з'явиться спливаюче сповіщення про захист від повторного голосування.
6. **Демонстрація 4 сценаріїв безпеки на «Стенді безпеки»:**
   - Перейдіть на вкладку **«🧪 Стенд безпеки»**.
   - **Картка 1 (Анонімний доступ):** натисніть `⚡ GET /users/me (Без токена)` — чорна консоль миттєво покаже червоний статус `401 Unauthorized` і відповідь сервера.
   - **Картка 2 (Автентифікація):** натисніть `❌ Вхід з невірним паролем` -> статус `401`; натисніть `✅ Вхід з вірними даними` -> статус `200 OK` та згенерований JWT-токен.
   - **Картка 3 (Вертикальне розмежування):** натисніть `🛑 Користувач лізе в /admin/dashboard` -> статус `403 Forbidden` (`Admin privileges required`); натисніть `👑 Адміністратор в /admin/dashboard` -> статус `200 OK`.
   - **Картка 4 (Горизонтальне розмежування / IDOR):** натисніть `🛑 User B редагує петицію User A` -> статус `403 Forbidden`; натисніть `🛑 User B редагує профіль User A` -> статус `403 Forbidden`; натисніть `✅ User A редагує власну петицію` -> статус `200 OK`.

## 6. ВИСНОВКИ

У ході виконання лабораторної роботи №2 було успішно реалізовано:
1. Базу даних користувачів із надійним збереженням гешів паролів (Bcrypt) та підключенням до реляційних моделей петицій і голосів.

3. Систему безсесійної автентифікації на основі токенів JWT (Bearer tokens) за стандартом OAuth2.

6. Захист від горизонтальної ескалації привілеїв (IDOR) як для сутностей предметної області (петиції), так і для профілів користувачів.
7. Базовий функціонал MVP: публікація, перегляд, фільтрація, модерація та голосування за петиції із блокуванням повторних підписів.
8. Повний набір модульних та інтеграційних тестів на фреймворку `pytest`, що покриває всі сценарії безпеки.
9. Сучасний, адаптивний веб-інтерфейс з інтерактивним стендом безпеки для швидкої та наочної демонстрації роботи системи викладачу.
