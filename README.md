# Local Petitions Service (Сервіс електронних петицій)

Веб-сервіс та REST API місцевих електронних петицій з рольовою моделлю доступу (RBAC), JWT-автентифікацією, захистом від атак IDOR, розділенням середовищ (Sandbox / Production) та автоматизованим CI/CD пайплайном.

Реалізовано в рамках навчальних робіт:
- **Лабораторна робота №2:** *«Користувачі, ролі користувачів та розмежування прав доступу»*.
- **Лабораторна робота №3:** *«Розділення конфігурацій для тестового і робочого середовищ. Впровадження CI/CD»*.

---

## 📌 Ключові можливості проєкту

### Безпека та контроль доступу (ЛР №2)
- **Хешування паролів:** криптографічний алгоритм **Bcrypt** із сіллю.
- **Безсесійна автентифікація:** цифрові токени **JWT (HS256)** з терміном дії.
- **Рольова модель (RBAC):** вертикальне розмежування доступу (`user` vs `admin`) через FastAPI Dependency `require_admin`.
- **Захист від IDOR:** горизонтальний контроль — користувачі можуть змінювати лише власні петиції та власний профіль (`403 Forbidden` при спробах порушення).
- **MVP петицій:** створення, каталог, пошук, фільтрація, підписання із захистом від повторного голосування (`400 Bad Request`), адмін-модерація статусів.

### Керування середовищами та надійність (ЛР №3)
- **Розділення конфігурацій:** зчитування налаштувань із `.env.sandbox` або `.env.production` через `pydantic-settings` без жодного hardcode.
- **Ізоляція баз даних:** використання окремих баз даних для пісочниці (`src/petitions_sandbox.db`) та продуктиву (`src/petitions_production.db`).
- **Режими безпеки:**
  - `DEBUG = False` у Production-середовищі.
  - Приховування внутрішніх стектрейсів коду: централізований обробник помилок повертає безпечне повідомлення без витоку деталей архітектури у Production.
  - Демо-дані завантажуються виключно у Sandbox (`SEED_DEMO_DATA=True`), робоча база залишається чистою.
- **CI/CD пайплайн:** автоматизований робочий процес у GitHub Actions (`.github/workflows/ci.yml`), що перевіряє код лінтерами та запускає набір тестів при кожному коміті або Pull Request.

## 🚀 Запуск застосунку в різних середовищах (Lab 3)

### 1. Тестове середовище (Sandbox)
У тестовому середовищі ввімкнено детальний режим налагодження (`DEBUG=True`), використовується база даних `petitions_sandbox.db` та завантажуються демо-користувачі й петиції.

**PowerShell (Windows):**
```powershell
$env:APP_ENV="sandbox"
uvicorn src.main:app --reload --host 127.0.0.1 --port 8000
```

**Bash / Linux / macOS:**
```bash
APP_ENV=sandbox uvicorn src.main:app --reload --host 127.0.0.1 --port 8000
```

---

### 2. Робоче середовище (Production)
У робочому середовищі вимкнено налагодження (`DEBUG=False`), вимкнено echo SQL-запитів, використовується чиста ізольована база `petitions_production.db`, а стектрейси приховуються від користувачів.

**PowerShell (Windows):**
```powershell
$env:APP_ENV="production"
uvicorn src.main:app --host 127.0.0.1 --port 8000
```

**Bash / Linux / macOS:**
```bash
APP_ENV=production uvicorn src.main:app --host 127.0.0.1 --port 8000
```

## 🧪 Автоматизоване тестування (Pytest)

Для запуску повного набору тестів (12 тестів для ЛР №2 та ЛР №3):

```bash
pytest -v
```

### Набір тестів перевіряє:
1. **Анонімний доступ (401 Unauthorized)** до приватних маршрутів.
2. **Автентифікація та помилки входу:** 200 OK + JWT при валідних даних; 401 при невірному паролі або логіні.
3. **Вертикальне розмежування (RBAC):** заборона доступу звичайного користувача до `/admin/dashboard` та модерації (403 Forbidden).
4. **Горизонтальне розмежування (IDOR):** заборона модифікації чужої петиції або чужого профілю (403 Forbidden).
5. **Бізнес-логіка петицій:** створення, підрахунок голосів, блокування повторних підписів (400 Bad Request).
6. **Конфігурації середовищ (Lab 3):** зчитування `.env.sandbox` та `.env.production`.
7. **Ізоляція баз даних:** розмежування файлів баз даних між Sandbox та Production.
8. **Безпека помилок 500:** маскування стектрейсу при `DEBUG=False` у Production та показ діагностики при `DEBUG=True` у Sandbox.

## ⚙️ CI/CD Пайплайн (GitHub Actions)

У репозиторії налаштовано конфігурацію автоматизованого пайплайну: [`.github/workflows/ci.yml`](.github/workflows/ci.yml).

### Як працює пайплайн:
- **Тригери запуску:** спрацьовує автоматично при `push` у гілку `main` та при створенні `pull_request`.
- **Етап 1: Lint (Контроль якості):**
  - Перевірка правил лінтингу: `ruff check src tests`
  - Перевірка форматування: `ruff format --check src tests`
- **Етап 2: Test (Автоматизовані тести):**
  - Запуск повного набору тестів: `pytest -v` у тестовому оточенні.

### Локальна перевірка пайплайну:
```bash
ruff check src tests
ruff format --check src tests
pytest -v
```
